Cheat sheet for your diagnostic misses

Built from your 13/37 diagnostic. Read it once, then drill.

⚠️ STUCK: you've missed these more than once, even after seeing the answer

1. JIT is a RUNTIME thing. javac: .java → .class (bytecode), at compile time. Then java starts the JVM, and the JIT compiler inside the JVM turns bytecode into machine code while the program runs. The JVM is part of the JRE. javac comes with the JDK, not the JRE. (You picked "javac" or "JIT runs at compile time" 3 times.)

2. Checked vs unchecked: one rule. Unchecked = RuntimeException and its subclasses, plus Error and its subclasses. Everything else under Exception is checked.
Unchecked: NullPointerException, ArithmeticException, NumberFormatException, ArrayIndexOutOfBounds, ClassCastException, IllegalArgumentException, VirtualMachineError, OutOfMemoryError.
Checked: IOException, FileNotFoundException, ClassNotFoundException, plain Exception.
→ throw new Exception() in a method without throws Exception is a compile error in that method, even if the caller has a try/catch.
→ throw new IllegalArgumentException() needs nothing declared.

3. An exception thrown INSIDE a catch block is NOT caught by the catch blocks next to it. Only finally runs, then it propagates up. (You picked "the next catch catches it" twice.)

4. Static = underlined. Italic = abstract. ~ = package (no modifier). (You picked "static in italics" twice.)

0. Your #1 habit to fix: picking the "happy path" answer

8 of your 24 misses were option A, the answer you get if the code "just works". When a code question looks easy, check these 5 traps before answering:
  • Compile error? Look for an unreachable checked catch, two default methods clashing, a missing initialisation, catch order, or a wildcard add.
  • Runtime exception? Removing from a list inside a for-each loop throws ConcurrentModificationException. A bad downcast throws ClassCastException.
  • Output formatting? A double prints as 100.0, not 100.
  • Which method actually runs? Dynamic binding applies even inside a constructor.
  • Does the reassignment reach the caller? No. Java passes the reference by value.

2. Java traps you missed (Ch2, 4, 5, 10)

  • Pass-by-value: r.setW(5) changes the caller's object, but r = new Rect() inside the method only changes the local copy. Changes made after that reassignment go to the new object.
  • Unreachable checked catch: catch (IOException e) when nothing in the try can throw it is a compile error. catch (Exception e) is fine, and so are unchecked exceptions.
  • Multiple catches: only the first matching catch runs, then finally, then the code after the try.
  • Overridden method called from a constructor: the subclass version runs, before the subclass's fields are initialised, so you see 0 / null.
  • Two interfaces with the same default method: compile error unless the class overrides it. Inside the override, pick one with A.super.show(). The order in the implements clause doesn't matter, and it's never a runtime error.
  • Type erasure: new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass() is true, and both print java.util.ArrayList.
  • Wildcards (PECS): with ? extends T you can only read (as T) and can't add. With ? super T you can add(T). List<Number> = new ArrayList<Integer>() is a compile error, because generics are invariant.
  • for-each + list.remove() → ConcurrentModificationException on the next iteration. Use Iterator.remove() or removeIf instead.
  • The 3 ways of overriding (slides): (1) a subclass overrides a superclass method, (2) implementing an abstract class's abstract methods, (3) implementing an interface's methods. Overloading and static hiding are not on the list.

5. Design principles (Ch9)

  • Symptoms of rotting design (exactly 3): Rigidity, Fragility, Immobility. Viscosity isn't on the slides.
  • Design goals: Reusability, Extensibility, Maintainability, to minimise the impact of change.
  • OCP: Bertrand Meyer, "open for extension, closed for modification". Red flag: a switch or if-else on a type.
  • LSP: Barbara Liskov, 1988. A subtype must be substitutable for its base type without changing behaviour. Red flags: an override that throws (Ostrich.fly) or changes the base's contract (Square.setHeight). "It compiles" and "real-world is-a" do NOT mean LSP holds.
  • ISP: a fat interface forces dummy implementations.
  • D in SOLID (slides): "Dependency Injection Principle", also called Inversion of Control. Depend on abstractions; a high-level class should not new a concrete low-level class.
  • SRP: one reason to change, which is the same as high cohesion.

6. Modelling an OO app (Ch8)

  • Steps: find nouns → classes, verbs → methods. Then attributes, relationships, multiplicities, then behaviour and interaction (sequence diagram), then enhance class details, implement, test.
  • CRC card template: Class name, Superclasses, Subclasses, Responsibilities, Collaborators. No attributes field. CRC cards come from Kent Beck and Ward Cunningham.
  • Stereotypes: entity holds data, boundary is the UI/interface to actors, control coordinates the logic.
