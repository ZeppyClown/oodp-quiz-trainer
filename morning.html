1. SOLID: how the lecturer tests it

The Slido deck had 9 Ch9 questions, in exactly 4 formats. You'll see the same 4 tomorrow:
  • "Which principle is most directly at risk?" + a code snippet (Q26). → Spot the smell using the table below.
  • "Which redesign best addresses the problem?" (Q24, 25, 27, 28, 32). → The answer is almost always: split it up, add an interface, or inject the dependency.
  • "What is printed, AND why is the design good?" (Q29, Q30). → Get the output, then pick the reason that mentions depending on the interface/abstraction.
  • A UML diagram → which principle? (Q31). → A client with a dashed arrow to an «interface», which the concrete classes realise (dashed line, hollow triangle), means DIP.

Your Slido traps:

  • Q26: an override that throws is LSP, not DIP. "Can the subclass stand in for the parent?" No, so LSP.
  • Q32: inheritance is NEVER the fix for coupling. "Make OrderService extend EmailClient" is always wrong. So are "make it static" and "merge the classes".
  • Q30: when the output options tie, the right reason is "X depends on the interface, not the concrete class". Any option saying "must be rewritten for each new type" describes the BAD design.
Coupling & cohesion (you missed 4 of these)
  • Goal: LOW (loose) coupling + HIGH cohesion. Remember it as "low-high".
  • Coupling = how much classes depend on each other. Fewer links = looser = better. More links is worse; class design ≠ a network.
  • Cohesion = how focused one class is. One job means high cohesion. Utils doing dates, email, tax and charts is the lowest cohesion. Cohesion is basically SRP.
  • Reduces coupling: talking through interfaces, and injecting dependencies through the constructor. Increases coupling: public fields, checking another class's type code, new-ing concrete classes.
  • "Interaction via interfaces promotes…" → loose coupling.
Facts they can ask word for word
  • Symptoms of rotting design (exactly 3):
    • Rigidity: hard to change; one change cascades into many required changes.
    • Fragility: one change breaks things in unrelated places.
    • Immobility: can't reuse a part, because it drags baggage with it.
    Cue: "cascade" → Rigidity. "breaks elsewhere" → Fragility. "can't reuse" → Immobility.
  • OO design objective: minimise the impact of change by managing dependencies. Design for Reusability, Extensibility, Maintainability.
  • OCP: Bertrand Meyer, "open for extension, closed for modification".
  • LSP: Barbara Liskov, 1988. As a contract: a subclass's pre-conditions are no stronger (it expects no more) and its post-conditions are no weaker (it provides no less).
  • ISP: many client-specific interfaces beat one fat, general-purpose interface.
  • D = "Dependency Injection Principle" (the slides' name), also called Inversion of Control. High- and low-level modules both depend on abstractions.
  • SRP: a class should have only ONE reason to change.

  • Slido Q08: parent method run() calls doWork(). That call means this.doWork(), and this is the Child, so the child's version runs. Answer B!, not A!.
  • Slido Q09: Parent p = new Child(); p.points gives Parent's field (10). p.getPoints() runs Child's method. Answer 10:30.
  • toString() comes from the nearest ancestor that defines it, not Object's default Class@hash.
  • A final method can't be overridden, so a subclass that declares it is a compile error.
B. Checked exceptions (missed 4 times, so read this twice)
  • Unchecked = RuntimeException and its subclasses, plus Error and its subclasses. Everything else is checked: IOException, FileNotFoundException, plain Exception, and your own MyEx extends Exception.
  • The test: if a method can throw a checked exception, you need a catch of that exception or one of its parents, or a throws on the method. Otherwise it's a compile error.
  • catch (RuntimeException e) does not catch an IOException (they're sibling branches). finally never counts as handling. (Slido Q42)
  • An exception thrown inside a catch skips the sibling catches; only finally runs, then it propagates.
  • Custom checked exception: class MyEx extends Exception. Custom unchecked: extends RuntimeException.
  • Methods on e: getMessage(), toString(), printStackTrace(). An exception is a run-time anomaly, not a syntax error.
C. Others from your misses
  • Streams are lazy. filter/map/peek do nothing until a terminal operation (forEach, collect, count, toList) runs. No terminal operation means the lambdas never print. (Slido Q38)
  • list.remove(1) on a List<Integer> removes by index.
  • Constructor chain: the parent part is always built first. Follow every this(...) and super(...) to the top, then print on the way back down.
  • Same package: everything except private is accessible. protected = package + subclasses elsewhere.
  • Abstract class vs interface: a class extends ONE class but implements many interfaces. Neither can be new'd. Interface fields are static final constants. Implementing a derived interface means implementing the base interface's methods too.

3. Not in the Slido deck, but in the quiz

The deck skipped Ch1, Ch2 and Ch8, and the real quiz covers them. The essentials:
  • Ch1: javac compiles .java to .class bytecode. The JIT inside the JVM compiles bytecode to machine code at run time. JDK ⊃ JRE ⊃ JVM.
  • Ch2: Java passes references by value, so reassigning a parameter doesn't affect the caller, but obj.setX() does. A double prints 100.0. A static field is shared by all objects.
  • Ch8: nouns become classes, verbs become methods. A CRC card has Class, Responsibilities, Collaborators (+ super/subclasses), and no attributes. entity = data, boundary = UI, control = logic.
  • UML (you scored 14/14, keep it): static is underlined, abstract is italic, ~ = package, # = protected. A filled diamond is composition; a hollow one is aggregation.
